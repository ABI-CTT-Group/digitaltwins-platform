# Glossary

Terms you meet in this repository, in the sense the platform uses them. For
where the code lives see [codemap.md](codemap.md); for how a request moves
between services see [request-flows.md](request-flows.md).

| Term | Meaning on this platform | Where it shows up |
|---|---|---|
| ADR | Architecture Decision Record: one file per significant design choice, with its context, the alternatives weighed and the consequences. Named `YYYY-MM-DD-title.md`. Compare *artifact*. | [docs/decisions/](decisions/README.md) |
| Airgap bundle | Everything needed to install on a host with no Internet access, kept on a persistent volume mounted at `/mnt/install_src`: a clean source checkout, the `env` and `secrets.env` inputs, frozen Docker images, apt packages, Python wheels and the Docker binaries. | [util/INSTALL-BUNDLE.md](../util/INSTALL-BUNDLE.md), [util/README.md](../util/README.md) |
| Approval | Committing a registered dataset to the platform (SEEK, Postgres and MinIO), then publishing whatever FHIR annotation it has. Whoever clicks Approve is the approver; there is no separate reviewer. Once approval finishes, the hubs say the dataset is **in the platform**. A tool or workflow is approved one build at a time. | [dataset_uploads.py](../services/api/app/routers/dataset_uploads.py), [tool_handoff.py](../services/builder/app/services/tool_handoff.py), [ADR](decisions/2026-11-06-card-status-sentence.md) |
| Artifact | A dated folder of design evidence for one change (implementation plan, task list, walkthrough), kept for audit in a regulated environment and committed with the code it relates to. It records what was planned at the time and may be stale; read the guides and ADRs for current behaviour. | [docs/plans/](plans/), [AGENTS.md](../AGENTS.md) |
| Assay | The runnable unit of work. It is a SEEK assay (the bottom of the ISA tree) tagged with exactly one of `script`, `notebook` or `gui`, which decides how it launches. Its run configuration (workflow, inputs, outputs, cohort) is in the Postgres `assay`, `assay_input` and `assay_output` tables. It is configured once and can run many times; each execution is an *assay run*. | [assays.py](../services/api/app/routers/assays.py), [dashboard.py](../services/api/app/routers/dashboard.py) |
| Assay run | One execution of an assay's workflow against its cohort. Its outputs collect in the *workspace* until they are submitted, which turns them into datasets. An assay keeps all its runs; a loop of rounds (annotate, train, repeat) is several runs of the same assays, not new assays. | `run_assay` and `upload_workspace_datasets` in [assays.py](../services/api/app/routers/assays.py) |
| Backend (of a GUI tool) | The optional containers a GUI tool's frontend calls at `/plugin/<expose>/`. To **deploy** a backend is to build its image and create its containers, once per build (minutes). To **start** it is to run an existing deployment's containers again (seconds). Launching the tool starts it, or deploys it if the build has no working deployment. A **deployment** is one build's backend record; each build has at most one. | [deploy_tool.py](../services/builder/app/engine/deploy_tool.py), [ADR](decisions/2026-11-05-start-gui-backends-on-launch.md) |
| Builder | The `builder` service: registers, builds, approves and deploys tools, GUI workflows' tools and plugins. The only service that runs plugin builds against the host Docker socket. Its tables are in the `portal` schema. Formerly the portal backend. | [services/builder/](../services/builder/README.md), [ADR](decisions/2026-10-21-builder-as-its-own-service.md) |
| Category (dataset) | Every dataset has one of four categories: `measurements`, `models`, `tools`, `workflows`. The category is also the MinIO bucket its files go in, and it is required on upload. | `DATASET_CATEGORIES` in [datasets.py](../services/api/app/routers/datasets.py), [ADR](decisions/2026-10-19-dataset-category-required.md) |
| Cohort | On an assay, `assay.cohort` holds the indices of the subjects to run, not a cohort name or a count. `{1}` means run `sub-1` only; empty means every subject. The portal's config dialog sends it as `number_of_participants`. | `_discover_samples` in [assays.py](../services/api/app/routers/assays.py), `set_assay_details` in [dashboard.py](../services/api/app/routers/dashboard.py) |
| Compute node (remote worker) | A separate VM that runs only an Airflow Celery worker. It joins the platform's Airflow over a private network and serves a queue such as `remote`. DAGs choose their queue from the `compute_queue` Airflow variable (`AIRFLOW_VAR_COMPUTE_QUEUE`). `REMOTE_COMPUTE=true` publishes Redis for it. | [compute-node-README.md](../util/compute-node-README.md), [services/airflow/compute-worker/](../services/airflow/compute-worker/) |
| DAG | An Airflow workflow definition (directed acyclic graph). A script workflow's DAG ships in its dataset's `code/` folder and is deployed to `services/airflow/dags/workflow_<seek_id>/`. Its `dag_id` must be `Path(__file__).parent.name`. An assay run triggers it once per input sample. | [workflow-dag-authoring.md](workflow-dag-authoring.md), [dag.py](../services/api/src/digitaltwins/workflows/dag.py) |
| Expose name | A plugin's unique name. It is the global its UMD bundle registers in the browser, the segment of its `/plugin/<expose>/` route, and its folder in the `tool-builds` bucket. | [plugin-system-architecture.md](../services/portal/docs/plugin-system-architecture.md) |
| FHIR | HL7 FHIR R4, the clinical data standard. The platform's HAPI FHIR server (`/fhir`) holds dataset annotations: measurement resources such as `ImagingStudy`, `Observation` and `DocumentReference`, a tool as an `ActivityDefinition`, a workflow as a `PlanDefinition`, a model as a `Device`. `dataset.fhir_status` tracks each push. | [dataset_fhir.py](../services/api/app/routers/dataset_fhir.py), [fhir_service.py](../services/api/src/digitaltwins/measurements/fhir_service.py) |
| FHIR annotation | Optional for every dataset: which FHIR resource each of a tool's or workflow's ports, or each measurement file, becomes, or a model's `Device` details. Approving an item publishes its annotation to FHIR; an item approved without one is not published to FHIR. | [dataset_fhir.py](../services/api/app/routers/dataset_fhir.py), [ADR](decisions/2026-11-06-optional-fhir-annotation.md) |
| FHIR Device | The FHIR resource a model dataset is published as: one `Device` per model, identified by the dataset UUID. Built by the platform because the FHIR libraries it uses have no model resource. | [models/fhir.py](../services/api/src/digitaltwins/models/fhir.py), [ADR](decisions/2026-10-12-model-fhir-device.md) |
| Gateway | The nginx `gateway` container: the platform's only public entry (ports 80 and 443). It terminates TLS, routes by path to each service, and hands every other path to `portal-frontend`. | [services/nginx/](../services/nginx/README.md) |
| GUI tool | A tool of type `gui`: a web app that runs in the portal. The builder builds its frontend into a UMD bundle, which the portal loads at `/tool-view`; an optional backend runs as containers behind `/plugin/<expose>/`. | [build_tool.py](../services/builder/app/engine/build_tool.py), [tool-plugin-view.vue](../services/portal/frontend/src/views/tool-plugin/tool-plugin-view.vue) |
| ISA (investigation, study, assay) | SEEK's hierarchy for describing research. An investigation sits in a project and groups studies; a study groups assays. The portal's study dashboard walks this tree. | [dashboard.py](../services/api/app/routers/dashboard.py), [populating_data.md](populating_data.md) |
| ISA project (prototype) | Everything a user uploads to describe one project: its ISA tree (investigations, studies, assays), each assay's workflow and cohort, and which planned datasets pass between assays. Uploading one will create a SEEK project; unlike a plain SEEK project, it also carries the assays' configuration. Only a frontend prototype exists, with a draft JSON format (`schemaVersion` `0.1-draft`): ISA projects are uploaded at `/catalogue/isa-project` and appear in the study dashboard under the "Study design sandbox" programme, stored in the browser only. | [IsaProjectHub.vue](../services/portal/frontend/src/views/isa-project/IsaProjectHub.vue), [types.ts](../services/portal/frontend/src/views/isa-project/model/types.ts), [sandbox.ts](../services/portal/frontend/src/views/isa-project/sandbox.ts) |
| Keycloak client | An application registered in the realm, with its own id, type (public or confidential) and redirect URLs. Each service has one; a confidential client's secret must match a `secrets.env` variable. | [architecture.md](architecture.md#keycloak-clients), [REALM.md](../services/keycloak/REALM.md) |
| LDH | NFDI4Health Local Data Hub, the extension of SEEK that the platform runs as its data catalogue. | [services/seek/ldh-deployment/](../services/seek/ldh-deployment/) |
| Measurement dataset | A dataset of category `measurements`: primary data per subject and sample, in SDS layout (`dataset_description.*` plus `primary/sub-<n>/sam-<n>/`). It can carry a FHIR annotation. | [validation.py](../services/api/src/digitaltwins/measurements/validation.py), [import-dataset.md](../services/api/docs/import-dataset.md) |
| Model dataset | A dataset of category `models`: a computational model in SDS layout, with `dataset_description` and its files under `primary/`. Published to FHIR as a `Device`; an assay input of this category reaches the DAG as `<name>_dataset_uuid`. | [models/validation.py](../services/api/src/digitaltwins/models/validation.py), [ADR](decisions/2026-10-12-model-dataset-ingest.md) |
| PACS, Orthanc, DICOM | DICOM is the medical imaging standard, for files and for the network protocol. A PACS stores and serves those images. The platform runs two Orthanc PACS servers (`orthanc-1`, `orthanc-2`), which de-identify every instance as it arrives. No platform code calls them. | [services/pacs/](../services/pacs/docker-compose.yml), [deidentification.py](../services/pacs/scripts/deidentification.py) |
| Planned dataset (prototype) | A dataset an assay output promises. It becomes a real dataset when a run of that assay is submitted; a run that has only finished doesn't count. Another assay in the same study can choose it as an input before it exists, and then reads the latest submitted run. A measurements dataset covers only the subjects its producer ran, so a consumer with a wider cohort gets a warning. The prototype greys it in the input picker and draws it as a dashed edge until it is submitted. | [isaProject.ts](../services/portal/frontend/src/views/isa-project/model/isaProject.ts) |
| Plugin | The builder's and portal's name for a built GUI tool: its UMD bundle, plus any backend containers. The builder writes its nginx route into a volume shared with `portal-frontend` and reloads that nginx. | [plugin-system-architecture.md](../services/portal/docs/plugin-system-architecture.md), [deploy_tool.py](../services/builder/app/engine/deploy_tool.py) |
| Programme, project | SEEK's top levels. A programme groups projects; a project owns investigations and has members. Registering a tool or workflow needs a `seek_project_id`, and the user must be a member of that project. | [programs.py](../services/api/app/routers/programs.py), [projects.py](../services/api/app/routers/projects.py), [seek-integration.md](seek-integration.md) |
| Realm | The Keycloak realm `digitaltwins`: the platform's users, groups, realm roles (`admin`, `researcher`, `clinician` and others) and clients. Rendered from a template and imported on Keycloak's first boot only. | [digitaltwins-realm.json.template](../services/keycloak/digitaltwins-realm.json.template), [REALM.md](../services/keycloak/REALM.md) |
| Registration | Bringing a dataset of any category into the platform: from the first upload request until the dataset is committed (to SEEK and Postgres) and its FHIR push has finished, successfully or not. A tool or workflow is also created, annotated, built and approved in the builder on the way. Deploying a DAG, starting a GUI tool's backend and deleting a dataset are not part of it. | [dataset_uploads.py](../services/api/app/routers/dataset_uploads.py), [workflow_tool_plugin.py](../services/builder/app/router/workflow_tool_plugin.py), [ADR](decisions/2026-11-04-central-registration-logging.md) |
| RO-Crate | Research Object Crate: a zip of files plus an `ro-crate-metadata.json` that describes them. The API registers each tool and workflow in SEEK with one RO-Crate POST, so SEEK's own extractors set its title, tags and CWL structure. | [seek/writer.py](../services/api/src/digitaltwins/seek/writer.py), [ADR](decisions/2026-09-30-register-tools-in-seek-via-single-ro-crate-post.md) |
| SDS | SPARC Dataset Structure, from the NIH SPARC programme: a folder layout (`primary/sub-<n>/sam-<n>/`, `code/`, `docs/`, ...) plus metadata spreadsheets (`dataset_description`, `subjects`, `samples`, `manifest`, ...). Every platform dataset uses it. The API maps the metadata files to Postgres tables. | [SDS dictionary](../services/api/src/digitaltwins/resources/version_2_0_0/sds_dictionary/), [core/uploader.py](../services/api/src/digitaltwins/core/uploader.py) |
| SEEK | The data catalogue (`/seek`), run as the LDH distribution of SEEK. It holds the ISA tree, SOPs, and every tool and workflow (as SEEK Workflows). The API calls it with the user's own token, so SEEK's permissions decide what each user sees. | [seek-integration.md](seek-integration.md), [seek/querier.py](../services/api/src/digitaltwins/seek/querier.py) |
| SOP | A SEEK Standard Operating Procedure. The platform uses one to link an assay to its workflow (assay, SOP, workflow): saving the portal's config dialog creates an SOP in the assay's project that links both. Postgres also keeps `assay.workflow_seek_id`, which names the DAG. | [assay_workflow_link.py](../services/api/src/digitaltwins/core/assay_workflow_link.py), [ADR](decisions/2026-10-05-link-assay-to-workflow-via-auto-created-sop.md) |
| Tool | A dataset of category `tools`: exactly one CWL `CommandLineTool` (`primary/tool_*.cwl`) and its code. Its type is `script`, `notebook` or `gui`. Registered in SEEK as a Workflow tagged `tool`, and published to FHIR as an `ActivityDefinition`. | [tools/validation.py](../services/api/src/digitaltwins/tools/validation.py), [ADR](decisions/2026-10-01-unified-tool-dataset-ingest.md) |
| Upload session | The API's resumable upload: create a session, send the files in parts, `finalize` (validate and stage), then commit, either at once (`on_finalize`) or after approval (`on_approve`, as the portal does). | [dataset_uploads.py](../services/api/app/routers/dataset_uploads.py) |
| Workflow | A dataset of category `workflows` with a `workflow_type`: one CWL workflow (`primary/workflow_*.cwl`) whose steps run tool CWLs. A `script` workflow runs as an Airflow DAG, a `notebook` workflow is staged into JupyterHub, and a `gui` workflow opens its GUI tool in the portal. Registered in SEEK as a Workflow tagged `workflow`, and in FHIR as a `PlanDefinition`. | [workflows/validation.py](../services/api/src/digitaltwins/workflows/validation.py), [ADR](decisions/2026-10-02-workflow-dataset-ingest.md) |
| Workspace | Where an assay run's outputs collect before they are submitted. Script runs write to the MinIO bucket `airflow-workspace` under `assay_<id>/<timestamp>/`. Notebook runs use the folder `assay_<id>/` in the user's JupyterHub server. | `upload_workspace_datasets` in [assays.py](../services/api/app/routers/assays.py), [jupyterhub/staging.py](../services/api/src/digitaltwins/jupyterhub/staging.py) |
