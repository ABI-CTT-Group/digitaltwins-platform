## Goal

Measurement datasets can be uploaded two ways: the portal GUI (`/upload-dataset/measurements`) and the REST API (`POST /digitaltwins-api/datasets`). Replace these with **one ingest implementation in digitaltwins-api**, used by both the portal GUI and REST clients. That implementation must:

- authenticate the user with Keycloak and check their role
- store data objects in the platform MinIO
- store metadata in the platform Postgres (`public.*`)
- optionally create a FHIR annotation, keyed by the dataset and subject UUIDs from platform Postgres, and push it to HAPI FHIR

This plan covers the `measurements` category only. Other categories keep their current behaviour.

## Requirements and how they are met

| Requirement | How it is met |
|---|---|
| Keycloak authentication | Every ingest endpoint is in digitaltwins-api and requires a valid Keycloak JWT. Writes also require the realm role `admin` or `researcher` (D7). The portal frontend sends its existing Keycloak token directly to `/digitaltwins-api`. |
| Optional FHIR annotation using dataset and subject UUIDs | UUIDs come from Postgres when the dataset is committed (D2). Every `primary/<sub>/<sam>` folder gets a subject and sample row even without spreadsheets (D11), so the UUIDs always exist. FHIR can be requested at upload time or added later (D3). A failed FHIR push leaves the dataset in place and can be retried (D4). |
| Upload through both the GUI and the REST API | Both use the same upload-session endpoints. The portal uses the **approval gate** (D10); REST clients can commit when they finalize. The REST API also keeps the one-shot `POST /datasets`. The `digitaltwins` library gets a Python client and an import CLI (D13). |
| Metadata in platform Postgres | Measurement uploads write the existing `public.dataset`, `dataset_description`, `subject`, `sample`, `dataset_mapping` and `manifest` tables, plus new tables for upload state and annotation, created by migrations (D6). |
| Files in platform MinIO | Files are stored in bucket `measurements` under `<dataset_uuid>/<relative path>`, the layout the API already uses. |

- The nginx route `/digitaltwins-api/` already allows 20 GB unbuffered request bodies ([platform-routes.conf:305-321](../../../services/nginx/snippets/platform-routes.conf#L305-L321)).
- MinIO's S3 API is not exposed at the edge, on purpose ([production.md:14-28](../../production.md)).
- **Nothing in the repo fetches data through FHIR `endpointUrl`s.** Airflow DAGs read MinIO directly, and the portal export clears those fields.

### Defects found during investigation that this work must fix

1. **Delete leaves orphans.** `Deleter` removes `dataset_mapping`, `manifest`, `dataset_description` and `dataset`, but leaves `subject` and `sample` rows ([postgres/deleter.py:76-84](../../../services/api/digitaltwins-api/src/digitaltwins/postgres/deleter.py#L76-L84)). It also never removes resources from HAPI.
2. **Error handling breaks when Postgres is disabled or the first insert fails.** `Uploader.upload_dataset` then references a `dataset_uuid_str` that was never assigned, so it raises `UnboundLocalError` and hides the original error.
3. **Basic auth is too slow for chunked uploads.** Basic auth does a Keycloak password grant on every request, so it can't be used for thousands of part uploads. The clients get a token once and then use Bearer.

## Decisions

| # | Decision | Chosen |
|---|---|---|
| D1 | Who owns ingest | **digitaltwins-api owns the whole pipeline. The portal becomes a UI only.** Upload sessions, classification, annotation, approval, commit and FHIR all move to the API. The portal frontend calls `/digitaltwins-api` directly, and the portal backend's measurement code is removed. |
| D2 | UUID authority | **Platform Postgres, at commit.** Dataset, subject and sample UUIDs come from `public.*` when the dataset is committed. Annotation drafts made before that key their entries by folder name, and the server stamps the UUIDs at commit. The slug mocks are deleted. |
| D3 | How REST users supply FHIR | **Both ways.** Inline, with `fhir=auto` or `fhir_descriptions` on the upload; or later, with `PUT …/fhir/annotation` and then `POST …/fhir/push`. |
| D4 | What happens when the FHIR push fails | **The dataset stays committed and FHIR can be retried.** `dataset.fhir_status` records the state. |
| D5 | Upload transport | **Move the portal's existing chunk protocol into the API unchanged**, as the smallest change to the current structure: no new container, no new nginx route, no new dependency. tus and presigned S3 were evaluated and deferred; see the ADR. |
| D6 | Schema changes | **Numbered SQL migrations in the API repo**, applied at API startup under an advisory lock and tracked in `schema_migrations`. The existing init SQL stays as the baseline and is not edited. |
| D7 | Authorization | **A realm-role check (`admin` or `researcher`) on uploads, approval, deletes and FHIR writes.** No ownership tracking. |
| D8 | Existing portal measurements | **Discard them.** A one-off purge removes the portal rows, their MinIO prefixes and their HAPI resources. Nothing is migrated. |
| D9 | Long-running work | Commit (MinIO and Postgres) and FHIR push run as **background jobs in the API process**. Their state is kept in Postgres and the client polls it. Finalize and approve return `202 Accepted`. There is no Celery or Airflow; compose runs one API replica. |
| D10 | **Approval gate (Q6)** | Each upload session has a `commit_mode`. With **`on_approve`** (used by the portal), finalize validates and **stages** the dataset. Nothing reaches MinIO or `public.*` until `POST /datasets/uploads/{id}/approve`. With **`on_finalize`** (the default for REST clients, the CLI and the one-shot endpoint), the dataset is committed straight after validation. Both modes run the same pipeline. |
| D11 | **Subjects and samples are optional (Q1)** | `subjects.xlsx` and `samples.xlsx` are optional. At commit, **every `primary/<sub>/<sam>` folder that no spreadsheet row covers gets a minimal `subject` / `sample` row** (`subject_name` / `sample_name` set to the folder name) and a `dataset_mapping` row, so subject and sample UUIDs always exist. Spreadsheet rows, when present, are used as they are today. |
| D12 | **File endpoint auth (Q2)** | `GET /datasets/{uuid}/files/{path}`, which the FHIR `endpointUrl`s point to, **requires a Bearer token and no particular role**. Nothing in the repo reads these URLs, the existing `/download` already requires credentials, and anonymous access to clinical data doesn't belong in a regulated environment. |
| D13 | **CLI import (Q3)** | Retire the portal CLI (`app.cli.import_measurement`), but **keep the wrapper scripts' usage**. `scripts/import-dataset.{sh,ps1,bat,command}` move to the API repo, copy the dataset into the digitaltwins-api container and run `python -m digitaltwins.cli.import_dataset`. That command signs in through the browser or device flow (ported from the portal), checks the role, and calls the same pipeline in-process (`on_finalize`, optional `--fhir auto`). Remote scripts use the library `UploadClient` over HTTP. |
| D14 | **Branches (Q4)** | Each repo gets a new branch named `feat/unified-measurement-upload`:<br>• **Portal:** stacked on the unmerged `feat/portal-postgres` (currently `e1b11bf`).<br>• **API:** starting from `90b1fd4`, the detached commit the platform pins (only on `origin/detached32`).<br>• **Platform:** starting from `dev_chinchien`. |

## Target design

### Flow

```
                    ┌──────────────── digitaltwins-api ─────────────────────────────────┐
Portal GUI ─┐       │ 1 POST /datasets/uploads  {commit_mode, fhir?}   (role check)      │
            ├─JWT─▶ │ 2 PUT  /datasets/uploads/{id}/parts/{rel}?n=&of=   (staging vol)   │
Script /    │       │ 3 POST /datasets/uploads/{id}/finalize                             │
UploadClient┘       │      sync: assemble + strict SPARC validation → 400 on error       │
                    │      on_finalize ──────────────────────────────┐                   │
                    │      on_approve → status=staged                │                   │
                    │ 4 (staged) GET  …/uploads/{id}/fhir/tree       │  folder-keyed     │
                    │            PUT  …/uploads/{id}/fhir/annotation │  draft, no UUIDs  │
                    │ 5 POST …/uploads/{id}/approve ─────────────────┤                   │
                    │                                                ▼                   │
                    │   202 → job: Postgres rows (+ D11 derived rows) + MinIO (one unit) │
                    │          → stamp UUIDs into draft → dataset_fhir_annotation        │
                    │          → if FHIR requested / draft present: FHIR push job        │
                    │ 6 (committed) GET/PUT /datasets/{uuid}/fhir/…, POST …/fhir/push    │
                    └────────────────────────────────────────────────────────────────────┘
                             │ public.* (Postgres)  │ measurements/<uuid>/ (MinIO)  │ HAPI
```

- **Portal:** Information step (1–3, `on_approve`), then Annotation step (4), then the Approval dialog (5). Approval commits the dataset and pushes FHIR, just as "Approval" does today. If the FHIR push fails, "Retry FHIR" calls `POST /datasets/{uuid}/fhir/push`.
- **REST, chunked:** steps 1–3 with `on_finalize`, then optionally step 6.
- **REST, one-shot:** `POST /datasets` does steps 1–3 with `on_finalize` in a single request. It streams to disk, runs the same validation and commit in the request, and returns `201` with `dataset_uuid`. If inline FHIR was requested, it queues the FHIR job and returns `fhir_status`.
- **CLI:** runs the same functions in-process, with `on_finalize`.

### Endpoints (digitaltwins-api)

| Method and path | Role | Notes |
|---|---|---|
| `GET /datasets/uploads/config` | auth | `max_upload_bytes`, `max_part_size`. Replaces the portal's `/config`. |
| `POST /datasets/uploads` | admin/researcher | Body: `name`, `description`, `category` (`measurements`), `source_kind` (`folder`\|`zip`), `manifest`, `commit_mode` (`on_finalize` by default, or `on_approve`), and optionally `fhir` (`none`\|`auto`) or `fhir_descriptions`. Returns `upload_id` and `max_part_size`. |
| `PUT /datasets/uploads/{id}/parts/{rel_path}?n=&of=` | admin/researcher | Raw `application/octet-stream` body |
| `GET /datasets/uploads/{id}` | auth | Status, received parts and bytes (for resume), `failure_*`, and `dataset_uuid` once committed |
| `GET /datasets/uploads` | auth | Lists sessions that aren't committed (`receiving`, `staged`, `processing`, `failed`) for the portal overview |
| `POST /datasets/uploads/{id}/finalize` | admin/researcher | `400` if validation fails; the session stays `receiving` and its parts are kept. With `on_finalize` → `202` (commit job). With `on_approve` → `200`, `status=staged`. |
| `GET /datasets/uploads/{id}/fhir/tree` | auth | For staged sessions: tree plus prefilled descriptions, keyed by folder name (replaces the portal's `/{id}/tree`) |
| `GET` / `PUT /datasets/uploads/{id}/fhir/annotation` | auth / admin,researcher | Draft descriptions for a staged session |
| `GET /datasets/uploads/{id}/fhir/preview` | auth | Dry-run `fhir.json` for the draft, with placeholder UUIDs |
| `POST /datasets/uploads/{id}/approve` | admin/researcher | `staged` or `failed` → `202` (commit job, then FHIR push if a draft exists). This is the portal's Approval. |
| `DELETE /datasets/uploads/{id}` | admin/researcher | Cancel: removes the parts, the staged copy and the session |
| `POST /datasets` | admin/researcher | The existing one-shot endpoint, rewritten to stream to disk. `category=measurements` goes through the new pipeline with `on_finalize`. |
| `GET /datasets/{uuid}` / `GET /datasets?categories=measurements` | auth | Existing endpoints; they now include `fhir_status` |
| `GET /datasets/{uuid}/fhir/tree` | auth | Tree plus prefilled descriptions carrying the real UUIDs |
| `GET` / `PUT /datasets/{uuid}/fhir/annotation` | auth / admin,researcher | Stored descriptions (camelCase, as fhir-cda expects) |
| `POST /datasets/{uuid}/fhir/push` | admin/researcher | `202`. Handles both the first push and retries. Before pushing it removes earlier resources, found by `identifier=dataset_uuid`. |
| `GET /datasets/{uuid}/fhir/preview` | auth | Dry-run `fhir.json`, or the stored one once pushed |
| `GET /datasets/{uuid}/files/{path}` | auth (D12) | Streams one object from MinIO. The FHIR `endpointUrl` values point here. |
| `DELETE /datasets/{uuid}` | admin/researcher | Existing endpoint, now also removing HAPI resources, `subject` and `sample` rows, the annotation and the local cache (fixes defect 1) |

The `fhir/*` handlers are written once and take a *target* that is either a staged session (with a folder-keyed draft) or a committed dataset (stamped with UUIDs). Only the routing is duplicated.

### State

- **`upload_session.status`**:
  - `receiving` → `staged` (`on_approve`, after finalize) → `processing` (approve) → `completed` or `failed`
  - `receiving` → `processing` (`on_finalize`, after finalize) → `completed` or `failed`
  - `receiving` or `staged` → *(deleted)* on cancel
  - `failed` records `failure_stage` (`commit`) and `failure_message`. The staged copy is kept, so the session can be approved or finalized again.
  - At startup, a sweep marks any session left in `processing` as `failed`.
- **`dataset.fhir_status`**: `none` → `pending` → `pushing` → `completed` or `failed`.
  - A push is accepted from `none`, `failed` or `completed`; pushing a `completed` dataset again updates it.
  - The same startup sweep applies to `pushing`.
- **Mapping to the portal's current statuses**, which the card UI already shows:

  | Portal status | New state |
  |---|---|
  | `pending_upload` | `receiving` |
  | `pending` | `staged` |
  | `uploading` | `processing`, or `fhir_status=pushing` |
  | `submit_failed` | session `failed` |
  | `fhir_failed` | `fhir_status=failed` |
  | `completed` | `fhir_status=completed`, or `none` if there was no annotation |

### Schema changes (migration `0001`)

- `upload_session`: `upload_id uuid PK`, `category`, `name`, `description`, `source_kind`, `commit_mode`, `status`, `failure_stage`, `failure_message`, `fhir_mode` (`none`\|`auto`\|`descriptions`), `fhir_descriptions jsonb` (inline request, or the staged draft), `dataset_uuid uuid NULL FK→dataset ON DELETE SET NULL`, `created_at`, `updated_at`. The part manifest stays in the chunk store's JSON file on the staging volume, as in the portal today.
- `dataset_fhir_annotation`: `dataset_uuid uuid PK FK→dataset ON DELETE CASCADE`, `descriptions jsonb`, `updated_at`.
- `dataset`: add `fhir_status varchar NOT NULL DEFAULT 'none'` and `fhir_failure_message text`.

### UUIDs and FHIR identifiers

- `dataset.uuid` → `dataset_uuid`
- patient `uuid` → `subject_uuid`, looked up in `dataset_mapping` by `subject_id` (the `primary/<sub>` folder name)
- Observation, ImagingStudy and DocumentReference `uuid` → `sample_uuid`, looked up in `dataset_mapping` by `sample_id` (the `primary/<sub>/<sam>` folder name)
- endpoint `uuid` → `uuid5(sample_uuid, "endpoint")`, which is deterministic, so a re-push keeps the same value

UUID fields are **owned by the server**. The server overwrites any `uuid` a client puts in `fhir_descriptions`, a staged draft or the annotation, matching entries by patient `name` and resource `samplePath`. Drafts and inline descriptions can therefore be written before any UUIDs exist.

**Subjects and samples (D11):**
- For `category=measurements`, `Uploader` goes on inserting rows from the spreadsheets, if they are present.
- After that, for each `primary/<sub>/<sam>` folder that `dataset_mapping` doesn't already cover by `(subject_id, sample_id)`, it inserts the missing `subject` and/or `sample` row, named after the folder, together with its mapping row.
- A subject folder that has no sample folders can't be mapped: the `dataset_mapping` primary key includes `sample_uuid`. Such folders are reported as warnings in the finalize response and in `/fhir/tree` (see Q7).

### Files and local cache

- The staging volume is a new named volume `${PROJECT_NAME}_dataset_staging`, mounted in the API at `DATASET_STAGING_DIR`. It holds chunk parts, staged datasets and post-commit caches.
- **Staged sessions are kept until they are approved or cancelled.** The TTL doesn't apply to them, matching the portal's `pending` behaviour today.
- After a commit, the extracted copy stays as a **local cache**, because classify and FHIR build read files from disk (fhir-cda globs directories and pydicom reads headers). It is removed after a successful FHIR push, when the dataset is deleted, or by a TTL sweep (default 7 days). If the cache is gone when `/datasets/{uuid}/fhir/tree` or `/fhir/push` is called, the job downloads the dataset from MinIO again with the existing `Downloader`.
- The built `fhir.json` is stored at `measurements/<dataset_uuid>/fhir.json`.

## Steps

The work spans three repositories and is delivered as **three PRs, merged in order**, all on branches named `feat/unified-measurement-upload` (D14):

1. API submodule
2. Portal submodule, stacked on `feat/portal-postgres`
3. Platform repo: compose, env, submodule bumps, docs, this plan and the ADRs

TDD applies to every step: write the test, watch it fail, then implement. Existing API tests are integration tests against live services. New tests are **unit tests with fakes** (MinIO and HAPI clients injected) plus **integration tests marked `@pytest.mark.integration`** against the compose stack.

### Part A — digitaltwins-api submodule

**A1. Migration runner and migration `0001` (D6)**
- `src/digitaltwins/postgres/migrate.py` applies `src/digitaltwins/postgres/migrations/NNNN_*.sql` in order.
  - Each file runs in its own transaction.
  - The whole run is serialized with `pg_advisory_lock`.
  - Applied versions are recorded in `schema_migrations(version, applied_at)`.
- It runs from the FastAPI lifespan at startup, and can also be run as `python -m digitaltwins.postgres.migrate`.
- Add `0001_upload_session_and_fhir.sql` with the schema changes above.
- *Verify:* integration tests on a fresh DB (after the init SQL) and on a DB that has already been migrated. The second run does nothing, and two runners started together don't conflict.

**A2. Role-checking dependency (D7, D12)**
- `auth_bearer` and `auth_basic` also return the decoded claims.
- Add a `require_upload_role` dependency that allows realm roles `admin` or `researcher`, returns `403` otherwise, and `401` when no token is sent.
- *Verify:* unit tests with tokens signed by a test RSA key cover each role, a missing role, an expired token and a Basic token.

**A3. Port the ingest core into the library (no HTTP yet)**
- New package `src/digitaltwins/measurements/`, ported from the portal with its tests:
  - `chunk_store.py`
  - `validation.py` (the strict SPARC structure check; subjects and samples not required)
  - `classifier.py`
  - `fhir_adapter.py`
  - `fhir_service.py` (apply descriptions, compute endpoint URLs, push, delete by identifier)
- Add `fhir-cda==1.2.5`, `digitaltwins-on-fhir==1.4.0` and `pydicom==2.4.4` to `requirements-prod.txt`, at the portal's locked versions.
  - *Implementation note:* `nibabel` and `pynrrd` were dropped from this list. fhir-cda doesn't import them; the portal uses them only for plugins.
  - *Implementation note:* the dataset zip extractor skips only `__MACOSX/`. The portal's `node_modules/`, `.git/`, `dist/` and `build/` blacklist is meant for plugin source code, and on a dataset it would silently drop a data folder named `build`.
  - *Implementation note:* the ingest core also includes `tree.py` (the auto-annotation tree, ported from the router's `/tree`). It leaves UUIDs empty, adds a top-level `samplePath` to each resource, and reports subject folders without samples as `warnings` (Q7).
  - *Implementation note:* HAPI push/delete and endpoint-URL computation are ported in A8, together with their tests.
- *Verify:* the ported portal tests (`test_measurement_chunk_store`, `test_measurement_classifier`, `test_validate_sparc_structure`) pass in the API repo. New tests cover archive safety, and an end-to-end tree and `fhir.json` build on `tests/data/example_sds_dataset`, which is identical to the platform's `tests/data/example_sds_dicom`.

**A4. Ingest pipeline, derived subjects and samples, UUID stamping**
- `Uploader.upload_dataset` gains, for measurements, the derived subject and sample rows (D11). Fix defect 2.
- `measurements/pipeline.py`:
  - `commit(session)` runs `Uploader.upload_dataset` (Postgres and MinIO in one unit), records `dataset_uuid`, then stamps and copies any draft or inline descriptions into `dataset_fhir_annotation`.
  - `stamp_uuids(descriptions, dataset_uuid, mapping)` implements the UUID rules above.
  - `build_and_push_fhir(dataset_uuid)` uses the local cache, or downloads the dataset if the cache is gone.
  - *Implementation note:* `build_and_push_fhir` moved to A8, next to the HAPI client it needs.
  - *Implementation note:* `Uploader.upload_dataset` also gained an optional `dataset_name`, because staged datasets live at `<staging>/datasets/<upload_id>/`. `check_descriptions_match(descriptions, dataset_root)` validates inline descriptions and drafts against the folders **before** commit, so stamping after commit can't fail.
  - *Implementation note:* if `samples.xlsx` names a subject that `subjects.xlsx` lacks, only that subject row is derived, and the spreadsheet's sample row is kept.
- *Verify:* unit tests show that:
  - a dataset without spreadsheets gets one subject or sample row per folder
  - one with partial spreadsheets gets only the missing rows
  - `stamp_uuids` overwrites client UUIDs, rejects an unknown `samplePath` with a 400, and produces deterministic endpoint UUIDs

  An integration test checks that after a commit the rows in `public.*` and the MinIO keys under `<dataset_uuid>/` exist.

**A5. Background jobs and the startup sweep (D9)**
- A small job runner in the API process, using `asyncio.to_thread`. Job state lives in the `upload_session` and `dataset.fhir_status` columns, not in memory.
  - *Implementation note:* this uses FastAPI's built-in `BackgroundTasks` instead of a custom `asyncio.to_thread` runner. It runs in the same process after the response is sent, with less code and the same guarantees for D9. Jobs never raise; they record failures on the row.
  - *Implementation note:* the staging layout (`staging.py`) is `<DATASET_STAGING_DIR>/chunks/upload_<id>/` for parts and `<DATASET_STAGING_DIR>/datasets/<upload_id>/` for the validated dataset root, which is later kept as the cache.
- The startup sweep sets stuck `processing` and `pushing` states to `failed`. It also covers `pending`, because a queued push that never started is stuck just the same.
- *Verify:* unit tests show that a job that raises ends in `failed` with a message, and that the sweep resets stuck rows.

**A6. Upload-session endpoints, including staged annotation and approval (D10)**
- New router `app/routers/dataset_uploads.py` with the session endpoints in the table above.
  - *Implementation note:* the router is registered **before** `datasets`, because `GET /datasets/{dataset_uuid}` would otherwise capture `/datasets/uploads`.
  - *Implementation note:* `approve` also retries a `failed` commit. The staged copy is kept, so this works for `on_finalize` sessions too.
  - *Implementation note:* `build_fhir_json` builds in a temp dir and never writes `fhir.json` into the dataset. A staged dataset is uploaded to MinIO as-is, so a stray file there would be published.
  - *Implementation note:* the portal's `GET /check-name` has no equivalent. Datasets are keyed by UUID and `dataset.dataset_name` isn't unique, so B2 drops the name-availability check.
  - *Implementation note:* sessions are limited to `INGEST_CATEGORIES = {"measurements"}`; other categories get a 400.
- *Verify:* TestClient tests cover:
  - the `on_finalize` path: init, parts, finalize with 202, poll until completed
  - the `on_approve` path: finalize to staged, put a draft, approve with 202, then completed with `fhir_status=pending`, and the annotation carries the real UUIDs
  - resume after partial parts
  - a validation failure that keeps the session in `receiving`
  - approve on a session that isn't staged returns 409
  - cancel of a staged session
  - `403` without a role

**A7. Rewrite the one-shot `POST /datasets`**
- Stream each part to disk with `shutil.copyfileobj` instead of `read()`.
- Guard against zip bombs by reusing `extract_uploaded_archive`, ported in A3.
- `category=measurements` goes through the new pipeline with `on_finalize`, plus optional inline FHIR. Other categories behave as before.
  - *Implementation note:* the response stays **200**, not 201, so existing clients don't break. The body gains `fhir_status` for measurements.
  - *Implementation note (security):* the old handler joined each part's `filename` to the temp dir unchecked, so `../` could escape it, and it used `zipfile.extractall`.
