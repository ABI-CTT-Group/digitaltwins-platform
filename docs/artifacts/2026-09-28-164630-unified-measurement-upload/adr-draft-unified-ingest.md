# Unify measurement dataset ingest in digitaltwins-api

- **Date:** 2026-09-28
- **Status:** Accepted

## Context

Measurement datasets can be uploaded in two ways, and the two are inconsistent.

**Portal GUI.** The flow is `/upload-dataset/measurements`, backed by portal-backend `/api/measurement/*`.
- Uploads are chunked and resumable, and the SPARC structure is strictly validated.
- It classifies samples, annotates them and pushes FHIR to HAPI.
- Metadata goes only into `portal.measurements`, never into the platform tables in `public.*`.
- The FHIR identifiers are slugs of folder names, so two datasets can collide.
- The backend checks no token.

**REST API.** The endpoint is digitaltwins-api `POST /datasets`.
- It checks the Keycloak JWT and writes `public.dataset`, `subject`, `sample`, `dataset_mapping` and `manifest`, with UUIDs generated by the DB.
- It stores files in MinIO under `<category>/<dataset_uuid>/`.
- It does almost no validation, has no FHIR support, and reads each upload fully into memory.

The requirements:
- Keycloak authentication
- optional FHIR annotation keyed by real dataset and subject UUIDs
- uploads from both the GUI and the REST API
- metadata in platform Postgres and files in platform MinIO

Neither path meets all of them. Several choices have to be made together:
- which service owns ingest
- where UUIDs come from
- how FHIR is supplied
- what a FHIR failure means
- how large uploads (tens of GiB) are transported

Two constraints shape these choices. First, MinIO's S3 API is deliberately not exposed at the public edge (`docs/production.md`). Second, classification and FHIR build (fhir-cda, pydicom) read files from a local directory.

## Alternatives Considered

### Ingest ownership

#### Option A: digitaltwins-api owns the whole pipeline, and the portal is only a UI (chosen)
- Pros:
  - One implementation, so the GUI and REST clients can't drift apart again.
  - The API already writes `public.*` and MinIO and already checks Keycloak JWTs, including portal-frontend tokens.
  - The portal's least-privilege `portal` DB role is unaffected.
- Cons:
  - The most porting work: chunk store, classifier, FHIR adapter and pipeline.
  - The API image gains the FHIR and imaging dependencies.

#### Option B: the portal stages uploads and the API commits them
- Pros: keeps the portal's backend flow.
- Cons:
  - Two staging implementations.
  - FHIR still has to move into the API for REST users.
  - The bytes have to be transferred again between the two services.

#### Option C: a shared library called in-process by both backends
- Pros: no change to transport.
- Cons: portal-backend would need write access to `public.*`, which contradicts the `portal`-role ADR (2026-09-28), and there would still be two HTTP surfaces to keep aligned.

### UUID authority

#### Option A: platform Postgres, when the dataset is committed (chosen)
Dataset, subject and sample UUIDs come from `public.dataset` and `dataset_mapping` when the dataset is committed. Annotation drafts made before that (the portal's staged Annotation step) key their entries by folder name, and the server stamps the UUIDs at commit.

`subjects.xlsx` and `samples.xlsx` stay optional. Every `primary/<sub>/<sam>` folder that no spreadsheet row covers gets a minimal `subject` / `sample` row named after the folder, so the UUIDs always exist.
- Pros:
  - One source of truth, and no more slug collisions.
  - Works with the portal's Approval gate and with inline REST annotation.
- Cons:
  - The UUIDs aren't visible while a dataset is staged.
  - Subject folders with no sample folders can't be mapped, because the `dataset_mapping` primary key includes `sample_uuid`.

#### Option B: the client may supply UUIDs, otherwise the server generates them
- Pros: stable IDs that come from upstream systems.
- Cons: needs rules for collisions and re-uploads, and nobody needs this today.

### When a dataset is committed

#### Option A: a per-session `commit_mode` (chosen)
- `on_approve`, used by the portal: finalize validates and stages the dataset. Nothing reaches MinIO or `public.*` until `POST /datasets/uploads/{id}/approve`.
- `on_finalize`, the default for REST clients, the CLI and the one-shot endpoint: the dataset is committed straight after validation.
- Pros:
  - The portal keeps its existing "Approval" step.
  - Scripts aren't forced through a manual gate.
  - Both modes run the same pipeline.
- Cons: one more state (`staged`), and the staged-draft annotation endpoints sit next to the endpoints for committed datasets.

#### Option B: always commit on finalize
- Pros: simpler states.
- Cons: removes the portal's Approval gate, which the product owner wants to keep.

### How FHIR is supplied

The chosen approach is **both**: inline on the upload (`fhir=auto` or `fhir_descriptions`), and afterwards through `PUT …/fhir/annotation` followed by `POST …/fhir/push`.

UUID fields are owned by the server. They are stamped from Postgres by matching the subject folder name and the `samplePath`, so a client can write inline descriptions before any UUIDs exist.

### FHIR failure semantics

#### Option A: the dataset stays committed and FHIR can be retried (chosen)
The state is recorded in `dataset.fhir_status`.
- Pros: data isn't lost because of a problem with HAPI, and this matches the portal's existing `fhir_failed` behaviour.
- Cons: a dataset can exist without FHIR resources, and consumers have to check `fhir_status`.

#### Option B: all-or-nothing, rolling back MinIO and Postgres
- Cons: a HAPI outage blocks every upload that asks for FHIR, and rolling back a multi-GiB MinIO upload is expensive.

### Upload transport

#### Option A: move the portal's chunked-upload protocol into the API (chosen)
- Pros:
  - The smallest change to the current structure: the client (`ChunkedUploader`) and server (`MeasurementChunkStore`) already work.
  - The existing `/digitaltwins-api/` nginx route already allows 20 GB unbuffered.
  - No new container and no new dependency.
  - Files land on disk, where validation and FHIR build can read them.
- Cons:
  - It's our own protocol. That is mitigated by a Python `UploadClient` in the `digitaltwins` library.
  - Upload bytes pass through the API.

#### Option B: tus, the open resumable-upload standard, through a tusd sidecar or served inside the API
- Pros: off-the-shelf clients in every language (Uppy, tus-js-client, tus-py-client), and standard resume semantics.
- Cons:
  - A new container or a new server library.
  - Hook wiring for Keycloak.
  - The frontend uploader would have to be rewritten.
  - More change than the current need justifies.
- **Deferred:** this is the upgrade path if external script users need resumable uploads in languages other than Python. The session and finalize control plane stays the same.

#### Option C: presigned S3 multipart straight to MinIO
- Pros: the cloud-native default, keeps upload bytes out of the API, and scales across replicas.
- Cons:
  - MinIO's S3 API would have to be exposed at the edge on its own hostname (SigV4 signs the host and path, which breaks under prefix rewrites), with CORS. That contradicts `docs/production.md`.
  - A presigned URL is needed for each file (a DICOM folder can hold ~10k).
  - The dataset has to be downloaded again so it can be validated and annotated.
- **Deferred:** revisit if storage moves to cloud object storage or the API runs as several replicas.

## Decision

- digitaltwins-api owns measurement ingest end to end. The portal frontend calls `/digitaltwins-api` directly with its Keycloak token, and the portal backend's measurement code is removed.
- Postgres generates the dataset, subject and sample UUIDs when the dataset is committed, and FHIR identifiers are derived from them. Subjects and samples missing from the spreadsheets are derived from the `primary/` folders.
- Each upload session has a `commit_mode`. The portal uses `on_approve`, which keeps its Approval step; REST clients default to `on_finalize`.
- FHIR can be supplied inline or afterwards. A failed push leaves the dataset committed, with `fhir_status=failed`, and can be retried.
- Uploads use the portal's chunk protocol, moved into the API (`/datasets/uploads/*`). The one-shot `POST /datasets` stays for small uploads and is rewritten to stream to disk.
- Commit and FHIR push run as background jobs in the API process, and their state is kept in Postgres.
- Uploads, approval, deletes and FHIR writes require the Keycloak realm role `admin` or `researcher`. The file endpoint that FHIR `endpointUrl`s point to requires a Bearer token.
- The portal CLI import is replaced by `digitaltwins.cli.import_dataset`, run in the API container by the same wrapper scripts, and by the library `UploadClient` for remote scripts.
- Existing portal measurements are discarded, not migrated.

## Consequences

- There is one ingest implementation and one set of endpoints, for both the GUI and scripts. The FHIR identifiers are real platform UUIDs.
- The portal backend no longer touches measurement data. Its `measurements` and `measurement_annotations` tables are dropped.
- The API image gains fhir-cda, digitaltwins-on-fhir, pydicom, nibabel and pynrrd, and needs a staging volume and access to HAPI FHIR.
- `subjects.xlsx` and `samples.xlsx` stay optional. Folder-derived `subject` / `sample` rows carry only a name until someone enriches them.
- Portal datasets reach MinIO and `public.*` only on Approval. Staged sessions stay on the API staging volume until they are approved or cancelled.
- FHIR `endpointUrl`s need a Bearer token to fetch, so anonymous FHIR consumers can't download the data.
- In-process jobs assume a single API replica. Scaling out would need a real job queue and shared staging storage, which is also the point at which to revisit presigned S3 uploads.
- The portal's CLI import moves to the API repo (`digitaltwins.cli.import_dataset` plus the same wrapper scripts), with the same usage as before.

## Amendments during implementation

- **Subject-level resources.** The portal lets users add Observations and DocumentReferences by hand, with no sample folder. Such a resource (one with no `samplePath`) is accepted as subject-level, and its UUID is `uuid5(subject_uuid, "<kind>:<n>")`, where n counts that subject's hand-added resources of that kind in order. The UUID stays server-owned and doesn't change when the same draft is saved again. An ImagingStudy still requires its sample folder. The alternative was to reject hand-added resources, which would have broken an existing portal feature.
- **Background jobs.** Jobs use FastAPI's built-in `BackgroundTasks` (in-process, run after the response), not a custom `asyncio` runner. The guarantees D9 needs are the same, with less code; state stays in Postgres, and a startup sweep fails interrupted jobs so they can be retried.
- **One-shot `POST /datasets`** keeps its `200` response, so existing clients don't break, and adds `fhir_status` for measurements.
- **FHIR cleanup walks the resource graph (found in the live smoke test).** `digitaltwins-on-fhir` tags only a dataset's Compositions with the dataset UUID. Patients carry the subject UUID and the other resources derived identifiers. Its `save()` also keeps any resource whose identifier already exists. So "delete by dataset identifier", the approach carried over from the portal, left most resources behind, and a re-push never applied an edited annotation. Dataset delete and pre-push cleanup now collect the graph from the Compositions and Patients by following references, restricted to the measurement resource types so shared Practitioners and Organizations are never touched, and delete referrers first. Searches send `Cache-Control: no-cache` to bypass HAPI's search-result cache. The alternative was changing the upstream library's identifier scheme or save semantics, which is out of this repository's control.
