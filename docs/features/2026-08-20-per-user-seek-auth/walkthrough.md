# Implementation Walkthrough: Per-User SEEK Authentication

This walkthrough details the changes made to enforce per-user Keycloak identity tracking when making SEEK API queries via `digitaltwins-api`. 

Previously, `digitaltwins-api` accessed SEEK using a global `SEEK_API_TOKEN` which bypassed per-user permissions. We have successfully implemented a system where Keycloak JWTs passed to the digitaltwins API are validated and forwarded directly to SEEK.

## 1. SEEK Backend Support for Keycloak JWT

We extended SEEK's authentication system to support Keycloak-issued JWT Bearer tokens without altering its core source code. 

- **Ruby Initializer:** We created a new file [keycloak_jwt_auth.rb](file:///home/clin864/Projects/digitaltwins-platform/services/seek/ldh-deployment/keycloak_jwt_auth.rb) mounted directly into the SEEK container.
- **Verification:** The initializer extracts `Authorization: Bearer <token>` headers, fetches the digitaltwins Keycloak realm's JSON Web Key Set (JWKS), and cryptographically validates the token.
- **Identity Mapping:** The Keycloak token's `sub` UUID is used to perform a lookup in SEEK's `identities` table to locate the exact corresponding SEEK user.
- **Monkey-patch:** We monkey-patched `AuthenticatedSystem.current_user` to insert this check at the very top of the authentication chain.

## 2. API Dependency Injection Refactoring

The `digitaltwins-api` was extensively refactored to stop using the global SEEK admin token and to instead use dependency injection to dynamically extract the user's Keycloak token on every request.

- **`auth.py` update:** Replaced boolean checks with dictionaries that extract and return both the `username` and the raw Keycloak `token`.
- **`query.py` update:** We eliminated the global `querier` singleton. We created a `get_querier` dependency that reads the caller's Keycloak token and instantiates a per-user `Querier` scoped to that request. All router endpoints (`get_studies`, `get_datasets`, etc.) now inject this dependency.
- **`assay.py` update:** The `run_assay` trigger now explicitly fetches and forwards the user's credentials to Airflow pipelines as well as verifying workflow details via a user-scoped querier.

## 3. Removal of Global Admin Token (`SEEK_API_TOKEN`)

With Keycloak dynamically injecting user-specific JWTs on a per-request basis into SEEK API calls, the global `SEEK_API_TOKEN` singleton became completely obsolete.

- We removed `SEEK_API_TOKEN` entirely from the deployment environments (`.env.template`, `secrets.env.template`, `digitaltwins-api/docker-compose.yml`, `src/digitaltwins/seek/querier.py`).
- We updated all documentation within the repository (`docs/seek-integration.md`, `docs/api_examples.md`, `docs/deployment.md`, `docs/production.md`, `docs/development.md`) to instruct users and developers to fetch and use a Keycloak JWT when making calls to the API or manually querying SEEK.

## 4. Airflow API Token Fix

During the migration to Keycloak authentication, we inadvertently replaced the method by which the API obtains tokens for triggering Airflow (`_get_api_token()`) with a Keycloak `client_credentials` request. Because the Airflow 3 REST API requires its own natively generated JWT to authenticate API requests, this caused `403 Forbidden` errors.

- We reverted the `_get_api_token()` in `digitaltwins-api/app/routers/assay.py` to its original logic: performing basic authentication against Airflow's `/auth/token` endpoint (using `AIRFLOW_USERNAME` and `AIRFLOW_PASSWORD`) to obtain a valid Airflow API token.
- With this fix, `digitaltwins-api` successfully delegates data requests to SEEK as the authorized Keycloak user, while successfully communicating with the backend Airflow server to execute workflows using the Airflow token.

## Usage Guide

- To authenticate against the API, obtain a token from Keycloak using the user's credentials or a client token, and supply it via the `Authorization: Basic <token>` (or Bearer token) header when querying the `/digitaltwins-api` endpoints.

## Verification
- We verified the end-to-end integration by querying `http://localhost/digitaltwins-api/studies` while authenticating as `admin` on Keycloak. 
- The JWT generated by Keycloak was successfully accepted by SEEK, and the correct studies restricted to the `admin` user's access were successfully queried.
- Unauthorized calls successfully return `401 Unauthorized`.
