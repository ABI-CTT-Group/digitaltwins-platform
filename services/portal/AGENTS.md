# Agent notes: services/portal

Read the root AGENTS.md first; this file adds only what's specific to this service.

The code map and run commands are in [README.md](README.md#for-developers). The rest of that README
is an end-user guide.

## Where changes go

- **The portal has no backend of its own.** Server-side changes go in `services/builder`
  (`/api/builder/...`) or `services/api` (`/api/...`).
- **Pages** go in `frontend/src/views/<area>/`, routes in `frontend/src/router/index.ts`.
- **Backend calls** go through `frontend/src/bootstrap/`: add a function to the area's module
  (`tool_api.ts`, `workflow_api.ts`, `platform_api.ts`, ...) rather than calling axios from a
  component. The default axios instance targets the builder (`/api/builder`); `dtApiAxios` in
  `http.ts` targets the platform API (`/api`).
- **Field names**: write camelCase. The interceptors in `bootstrap/http.ts` convert to and from the
  backends' snake_case. A name that differs by more than case needs an entry in
  `FE_TO_BE_ALIASES` (for example `toolMetadata` ↔ `plugin_metadata`). FHIR `descriptions` trees
  sent to the API are not converted.
- **Links to SEEK and JupyterHub** come from `frontend/src/config/platform-links.ts`; keep them
  relative.
- **portal-frontend's nginx** is `frontend/nginx.conf.template`. Every `proxy_pass` goes through a
  `set` variable. Only `BUILDER_PORT` and `MAX_UPLOAD_MB` are substituted (`NGINX_ENVSUBST_FILTER` in
  `docker-compose.yml`); a new variable must be added to that filter. Platform-wide routes belong in
  `services/nginx`, and `/plugin/*` routes are generated by the builder: never write them here.
- **`docker-compose.yml`**: the platform uses only `portal-frontend`. The other services in that file,
  and `docker-compose.override.yml`, serve the standalone stack only.

## Tests

- Put `<Name>.spec.ts` in a `__tests__/` folder beside the code it tests. Vitest picks up only
  `src/**/__tests__/**/*.spec.ts` (the `test` block in `vite.config.ts`), in jsdom.
- `src/testing/setup.ts` stubs the browser APIs Vuetify overlays need. Mount Vuetify components with
  `testVuetify()` from `src/testing/vuetify.ts`.
- Run `make test-frontend` (Node 20, offline, with its own cached `node_modules`) and
  `make lint-frontend` (eslint and vue-tsc).
- A change to `frontend/nginx.conf.template` also runs the builder's tests, which check it.

## Gotchas

- **Plugin bundles use the portal's Vue, Vuetify and Pinia.** `registerPlugins` in
  `bootstrap/index.ts` puts `Vue`, `Pinia`, `Vuetify` and `VueToastification` on `window`, and the
  builder builds plugin bundles with those names as externals (`app/engine/build_tool.py`). Don't
  remove or rename those globals.
- **`VITE_KEYCLOAK_*` are build arguments** (`docker-compose.yml`), baked into the bundle. Changing
  one needs an image rebuild.
- The image and `make test-frontend` install with Yarn 1 and `--frozen-lockfile`, so a dependency
  change must update `yarn.lock` in the same commit.
